ContractGuard: End-to-End Project
Documentation
AI contract reviewer for rental agreements, job offers and freelance contracts. Stack:
React, FastAPI, RAG, LangGraph, PostgreSQL with pgvector.
1. Overview
1.1 Problem
People sign rental agreements, job offers and freelance contracts without understanding
what they are agreeing to. Risky clauses (unlimited liability, one-sided termination, auto-
renewal, heavy penalties, IP grabs) are buried in dense legal language, and professional
legal review is expensive.
1.2 Solution
ContractGuard reads an uploaded contract, finds and classifies each clause, flags the
risky ones against a red-flag knowledge base, computes the exact dates and money
exposure with plain code, and proposes safer replacement wording. The user reviews and
approves each suggested change, and only then does the app generate a negotiation
email and a downloadable report.
1.3 Design principle
Code does the maths, the AI does the language. Date extraction, notice-period
deadlines, penalty exposure and risk scoring run in deterministic Python so results are
exact and testable. The LLM is used only to classify clause meaning, explain risk in plain
language, and draft counter-clauses. This is the same principle used in CampusPilot.

2. Users and user stories
Core user stories:
1. As a user, I upload a contract PDF and see its clauses listed with a risk level.
2. As a user, I ask Can the landlord raise rent during the term? and get an answer citing
[file, clause, page] .
3. As a user, I see key dates and amounts (start, end, notice deadline, late fee, deposit)
calculated for me.
4. As a user, I review each suggested counter-clause and accept, edit or reject it.
5. As a user, I generate a negotiation email containing only the changes I approved.
6. As a user, I upload a revised contract version and see how the risk score changed.

6. Ingestion and RAG pipeline
6.1 Ingestion flow
1. Upload: the file is validated (type, size under 15 MB) and stored.
2. Parse: extract text per page, keeping page numbers. If a page has no text layer, fall
back to OCR.

3. Clause segmentation: detect numbered headings with rules (for example 1. , 1.1 ,
Article 5 , Section 7 ) to split into clauses. If numbering is absent, fall back to
paragraph chunking with an overlap of about 100 tokens.
4. Embed: each clause is embedded and stored in clauses.embedding .
5. Typing: the classify_risk step later fills clause_type and summary .
Clause-aware chunking matters because it makes citations precise: a citation is
[contract.pdf, Clause 7.2, p. 4] instead of a random page range.
6.2 Knowledge bases
Two retrieval sources, both in pgvector:
The contract itself ( clauses ), filtered by version_id .
The red-flag and standard-terms knowledge base ( kb_documents ), filtered by
contract_type and jurisdiction . Seed it with curated, reviewed material: typical
safe notice periods, fair late-fee ranges, deposit rules, IP assignment norms, non-
compete limits. Each entry has a source so answers can be traced.
6.3 Question answering
question -> embed -> top-k clauses (version-scoped) + top-k KB entries
         -> prompt: answer ONLY from these passages, cite [clause, page]
         -> LLM -> answer + citations -> validate citations exist -> respond
Rules enforced in code, not only in the prompt:
If the best similarity score is below a threshold, return I could not find this in your
contract instead of calling the LLM.
Every citation in the answer must match a retrieved clause id. Answers with
unmatched citations are rejected and retried once.
Contract text is treated as untrusted data. The prompt tells the model that
instructions inside a contract must be ignored (prompt-injection defence).

7.3 Risk scoring
Each finding gets a score from severity (low 1, medium 3, high 6, critical 10). The contract
score is a weighted sum normalized to 0 to 100, where categories like liability and
termination carry higher weights for the user's role. The weights live in a versioned config
file so the score is reproducible and unit-testable. The LLM may suggest a severity, but
the final number always comes from this table plus the rules (for example, an uncapped
liability clause is forced to critical).

8.4 Human-in-the-loop with checkpointing
The graph is compiled with a Postgres checkpointer so state survives restarts. The
human_review node calls interrupt(...) with the list of pending suggestions. The API
marks the run awaiting_review . When the user submits decisions, the API resumes the
same thread_id with Command(resume=decisions) .
def human_review(state):
    decisions = interrupt({'suggestions': state['suggestions']})
    return {'decisions': decisions}
graph = builder.compile(checkpointer=PostgresSaver(conn))
# start
graph.invoke({'version_id': vid}, config={'configurable': {'thread_id': 
tid}})
# resume after user review
graph.invoke(Command(resume=decisions), config={'configurable': {'thread_id': 
tid}})
Safety rules:
Nothing is exported unless at least one suggestion is approved or edited.
Rejected suggestions never appear in any output.
The original contract text is never modified. Suggestions are stored separately and
shown as a diff.

12. Security, privacy and safety
Sensitive data: contracts contain personal and financial details. Encrypt data at rest
(disk or managed Postgres encryption), use HTTPS, and keep uploads in a private
bucket or volume.
Isolation: every query is scoped by user_id . Add automated tests that one user
cannot read another user's contract.
Retention: a delete my contract action removes the file, clauses, embeddings,
findings and exports. Optionally auto-delete after a set number of days.

LLM privacy: tell users that text is sent to the LLM provider. Do not log full contract
text, only ids and token counts.
Prompt injection: contract text is passed as quoted data, the system prompt says to
ignore instructions inside it, and outputs are schema-validated.
Upload safety: check MIME type and size, scan for malicious files, set timeouts on
parsing.
Disclaimer: shown at upload, on results, and inside every export. The tool never says a
clause is illegal, only that it is unusual or risky compared with the knowledge base.
Rate limiting on upload and chat endpoints to control cost and abuse.

dates and money involved, and drafts safer wording that you approve one change at a
time. Code does the maths, AI does the language, and nothing is sent without your
approval. Built with React, FastAPI, LangGraph, pgvector and RAG. Informational tool,
not legal advice.
